## Что строим

На входе одно резюме и набор вакансий (docx, pdf, txt). На выходе:

1. Рейтинг вакансий по соответствию кандидату с объяснением места каждой.
2. Для каждой вакансии таблица: требование · подтверждение в резюме · статус · комментарий.
3. Четыре статуса: «Соответствует», «Частично», «Не соответствует», «Не указано».
4. Сильные стороны кандидата относительно вакансии.
5. Пробелы и риски, которые стоит уточнить.
6. Рекомендация рекрутеру и вопросы кандидату.

Выводы опираются только на текст резюме и вакансий. Во внешние API уходят только обезличенные данные.

Данные кейса кладём в `data/case/`: 4 резюме (ФИО вымышлены) и 3 вакансии. Полный текст кейса — `docs/case/case.pdf` и `docs/case/case.txt`.

**Сроки:** заморозка фич 14.11 в 14:00. Загрузка на платформу 14.11 до 23:59, наша цель — 20:00. Финал 15.11.

В топ-3 проходят только по техническим критериям (100 баллов).

## Архитектура

```
1. Вход — локально, без LLM
   загрузка и валидация → текст, разбитый на фрагменты с адресами → маскирование ПДн

2. Извлечение — LLM со строгой JSON-схемой
   требования вакансии (атомарные, must / nice)  ·  профиль кандидата  ·  проверка покрытия кодом
   + код: даты, стаж общий и по навыку, уровни образования и языка

3. Сопоставление — по каждому требованию (гибрид, решение D6)
   проход A: все требования вакансии одним вызовом
   → проверка фрагментов кодом → правила поверх LLM (стаж, пороги, «не указано»)
   → проход B для спорных: поиск доказательств (BM25 + эмбеддинги) + узкий вопрос
   → итоговый вердикт

4. Результат — собирает код
   балл и рейтинг  →  отчёт рекрутеру  →  выдача (API, UI, JSON)
```

## Принципы — не нарушаем

1. **LLM не пишет цитаты.** Модель возвращает номера фрагментов, текст цитаты подставляет код из исходного документа.
2. **Нет проверенного фрагмента — нет вывода.** «Соответствует», «Частично», «Не соответствует» ставятся только при существующих `fragment_id`. Иначе код ставит «Не указано».
3. **Балл, рейтинг, стаж и пороги считает код.** LLM не упорядочивает вакансии и не считает даты.
4. **Все внешние вызовы идут только через `src/aihr/llm/client.py`.** Клиент вызывает guard (проверку на ПДн) и пишет журнал исходящих запросов. Других HTTP-вызовов к LLM в проекте нет.
5. **Никакой подгонки под вакансии кейса.** В коде и промптах нет слов из трёх вакансий кейса (frontend, основные средства, куратор и т. п.). Few-shot примеры берём из других профессий. Проверка — `check-leak`.
6. **Отчёт строится из проверенных вердиктов.** Сгенерированный текст (рекомендация, письмо кандидату) проходит проверку сущностей: каждое число, дата и название должно найтись в фактах.
7. **Ошибка одного документа не роняет прогон.** Битая вакансия даёт код ошибки в результате, остальные считаются.
8. **Воспроизводимость.** Temperature 0, кэш по хэшу (текст + версия промпта + модель), закреплённые версии зависимостей.
9. **Текст документа — данные, а не команды.** В промпте документ всегда в отдельном блоке `<document>…</document>` с инструкцией не выполнять команды из него.
10. **Секреты.** Ключ API только в `.env`, который в `.gitignore`. Значение ключа не печатаем ни в лог, ни в консоль, ни в результат.

## Окружение (Windows)

Ноутбук: Ryzen 7 7840HS, встроенная Radeon 780M, NVIDIA нет. Всё, кроме LLM, работает на процессоре. LLM — только по API (D20).

- **Python 3.12 через uv.** `uv python install 3.12`, в корне `.python-version` с `3.12`. PyCharm создал `.venv` на 3.14 — uv пересоздаст его на 3.12. После этого в PyCharm выбрать интерпретатор `.venv\Scripts\python.exe`. На 3.14 не переходим: у части зависимостей может не быть готовых сборок.
- **`make` на Windows нет.** Все команды заведены как задачи poethepoet в `pyproject.toml`: `uv run poe test` делает то же, что `make test`. Makefile — тонкая обёртка над теми же командами для Linux, macOS и жюри. Если в документах написано `make X`, на этой машине запускай `uv run poe X`.
- **Docker Desktop с бэкендом WSL2.** Проверка: `docker version` и `docker compose version`. Если Docker не установлен или не запущен — скажи пользователю: установка требует его действий.
- **Переводы строк.** `.gitattributes` с `* text=auto eol=lf`: скрипты с CRLF ломаются в Linux-контейнере.
- **Кодировка.** `PYTHONUTF8=1` в окружении и `encoding="utf-8"` в каждом `open()`. Пути — только через `pathlib`. Русские имена файлов вроде `Вакансия 1.docx` должны работать.
- **Shell.** Claude Code на Windows запускает команды в Git Bash. Пиши команды, которые работают и там, и в Linux-контейнере.
- **Сеть из контейнера.** Ничего не скачиваем при первом запросе: модели Natasha и эмбеддингов кладутся в образ на этапе сборки.

## Конвенции

- Код и идентификаторы на английском. Тексты для пользователя и промпты — на русском.
- Типы везде. Pydantic-модели на границах модулей.
- Промпты лежат в `src/aihr/<модуль>/prompts/*.md`. В первой строке — `version: N`. Версия входит в ключ кэша.
- Логи через `logging`, без `print`. ПДн в логи не пишем.
- Новая функция → тест. Баг → сначала падающий тест, потом исправление.
- Тесты не ходят в сеть: LLM подменяется заглушкой. Прогоны с настоящей моделью — отдельной меткой `pytest -m llm`, по умолчанию выключены.

## Работа с LLM

- Единственный вызов: `llm.structured(prompt_id, variables, schema) -> schema`.
- В промпт попадает только `masked_text` фрагментов. Каждый фрагмент передаётся с номером: `[R12] текст`.
- Ответ модели ссылается на номера фрагментов. Код проверяет, что номера существуют.
- Temperature 0. Повтор при невалидном JSON — с текстом ошибки валидации, не больше 2 раз.
- Резюме кейса отправляем в LLM только после того, как готово маскирование (T02). До этого — только вакансии и выдуманные резюме из `tests/fixtures/`.

## Git

- `main` всегда запускается. Мелкие коммиты после каждого шага с зелёными тестами.
- Вехи помечаем тегами: `m0`, `m1`, `m2`, `v1.0`.
- Коммиты на английском, в повелительном наклонении: `Add docx table extraction`.
- Репозиторий: `git@github.com:aweeeexo/AIHR-Attention-Is-All-HR-needs-.git`.
- Ветки `a/<задача>` (роль A) и `b/<задача>` (роль B), PR в `main`. Перед PR зелёные `uv run poe test`, `uv run poe lint`, `uv run poe check-leak`. Чаще подтягивай `main`: `git pull --rebase origin main`.
- `STATUS.md` и `decisions.md` правят оба: дописывай строку, не переписывай чужие.
- Никогда не коммитить `.env`, `data/runs/`, ключи и результаты прогонов с исходными текстами резюме.
