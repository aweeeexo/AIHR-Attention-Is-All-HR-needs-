# Фронтенд для AIHR: что уже есть и что нужно сделать

Документ для того, кто делает фронтенд. Бэкенд готов: всё, что нужно показать, приходит из API готовым. Фронтенд ничего не считает и не придумывает, он только показывает.

## 1. Что за проект

Хакатон «ИИ в системе управления МФТИ», трек 3. На входе одно резюме (или пачка резюме) и набор вакансий в docx, pdf, rtf или txt. На выходе:

- рейтинг вакансий с объяснением места;
- таблица по каждой вакансии: требование · цитата из резюме · статус · комментарий;
- сильные стороны, пробелы, риски, вопросы кандидату, рекомендация рекрутеру, черновик письма;
- для пачки резюме — матрица «кандидаты × вакансии» и лучшие кандидаты на каждую вакансию.

Сроки: заморозка фич **14.11 в 14:00**, сдача 14.11 вечером, финал 15.11.

## 2. Что уже сделано (бэкенд)

| Часть | Состояние |
|---|---|
| Загрузка документов | docx (с таблицами и надписями), pdf, rtf, txt в любой кодировке; битые файлы дают код ошибки с подсказкой и не роняют прогон |
| Обезличивание | ФИО, контакты, адреса, даты рождения маскируются до любого вызова LLM; журнал всего, что ушло наружу |
| LLM | Любой OpenAI-совместимый провайдер; сейчас YandexGPT 5.1. Без ключа работает упрощённый режим без LLM |
| Извлечение | Требования вакансии (обязательные / желательные, пороги лет, образования, языка), профиль кандидата |
| Сопоставление | По каждому требованию: статус из 4, цитаты из резюме (подставляет код, не модель), комментарий. Гибридный поиск доказательств BM25 + эмбеддинги |
| Балл и рейтинг | Одна формула для всех вакансий, интервал неопределённости, метка «подходит / с оговорками / не подходит», объяснение места |
| Отчёт | Сильные стороны, пробелы, риски, вопросы, рекомендация, письмо, вывод для менеджера, экспорт в DOCX |
| Пакет резюме | Несколько резюме × вакансии: матрица, лучшие кандидаты на вакансию, полный отчёт по каждому |
| API | FastAPI, OpenAPI-документация на `/docs`, CORS для локального фронтенда |
| Текущий UI | Streamlit на :8501 — рабочий, его можно использовать как образец экранов |
| Развёртывание | Docker + Compose, 400+ тестов, проверка «чистой машины» |

Качество на нашем эталоне (200 пунктов, 12 пар резюме × вакансия): точность статусов 88%, лучшая вакансия угадана для 4 резюме из 4, ни одного «Не соответствует» там, где в резюме просто нет сведений. Подробно — `eval/report.md`.

## 3. Как поднять бэкенд

Нужны Docker Desktop и git.

```bash
git clone git@github.com:aweeeexo/AIHR-Attention-Is-All-HR-needs-.git
cd AIHR-Attention-Is-All-HR-needs-
cp .env.example .env        # без ключа LLM всё работает в упрощённом режиме — для вёрстки хватит
docker compose up --build   # первый раз ~5 минут: образ 3,5 ГБ с моделью эмбеддингов
```

- API: http://localhost:8000, документация и «попробовать запрос»: http://localhost:8000/docs
- Текущий UI для сравнения: http://localhost:8501

Ключ LLM попроси у владельца репозитория и положи только в `.env` (он в `.gitignore`). С ключом ответ на одно резюме идёт **1–3 минуты**, без ключа — несколько секунд.

**CORS.** По умолчанию API принимает запросы из браузера с `http://localhost:3000`, `:5173` и `:8501`. Другой адрес — переменная `CORS_ORIGINS` в `.env` через запятую.

## 4. API

Все ответы — JSON. Запросы синхронные: ответ приходит, когда всё посчитано. Ставь таймаут запроса **не меньше 10 минут** и показывай прогресс-заглушку («Считаем: загрузка → обезличивание → извлечение → сопоставление → балл → отчёт»).

| Метод | Путь | Вход | Ответ |
|---|---|---|---|
| GET | `/health` | — | `{"status":"ok","llm":"configured"\|"none","retrieval":"bm25+embeddings"\|"bm25","contracts_version":3}` |
| POST | `/match` | multipart: `resume` — один файл, `vacancies` — один или несколько файлов | `MatchResult` |
| POST | `/match/example` | `?resume=<часть имени файла>` (необязательно) | `MatchResult` на данных кейса |
| GET | `/example/files` | — | `{"resumes":[…],"vacancies":[…]}` — файлы примера для выпадающего списка |
| POST | `/match/batch` | multipart: `resumes` — несколько файлов (до 50), `vacancies` — несколько | `BatchResult` |
| POST | `/match/batch/example` | — | `BatchResult` на всех резюме и вакансиях кейса |
| GET | `/runs/{run_id}` | — | сохранённый `MatchResult` |
| GET | `/batches/{batch_id}` | — | сохранённый `BatchResult` |
| GET | `/runs/{run_id}/report/{vacancy_id}.docx` | — | файл DOCX (заголовок `Content-Disposition` с именем) |
| GET | `/runs/{run_id}/outbound` | — | `{"entries":[…]}` — что ушло во внешнюю LLM |

Ошибки API: `4xx/5xx` с `{"detail": "…"}` по-русски. Ошибки отдельных файлов (битый docx и т. п.) — это **не** ошибка API: они приходят в `errors` внутри результата.

```bash
curl -F resume=@resume.docx -F vacancies=@v1.docx -F vacancies=@v2.pdf localhost:8000/match
curl -X POST localhost:8000/match/example
curl -X POST localhost:8000/match/batch/example
```

Полные схемы — `src/aihr/contracts.py` и `docs/contracts.md`; живые примеры ответов — `docs/frontend/examples/`.

## 5. Что показывать: экраны и поля

### Экран 1. Загрузка

- Резюме: файл (docx, pdf, rtf, txt) или вставка текста. Вставленный текст отправляй как файл `резюме.txt` в UTF-8.
- Вакансии: несколько файлов или вставка текста (`вакансия.txt`).
- Кнопка «Пример из кейса» с выбором резюме из `/example/files` — для демо жюри это главная кнопка.
- Переключатель «Одно резюме / Пакет резюме».
- В шапке — состояние из `/health`: LLM подключена или нет, режим поиска.

### Экран 2. Результат по одному резюме (`MatchResult`)

| Что | Где в JSON |
|---|---|
| Режим (LLM / упрощённый) | `mode`: `"llm"` или `"fallback"` — при `fallback` покажи предупреждение |
| Ошибки файлов | `errors[]`: `filename`, `code`, `message`, `hint` — карточкой у файла |
| Предупреждения | `warnings[]` |
| Итог для менеджера | `ranking.summary` — крупно сверху |
| Карточки рейтинга | `ranking.items[]` по порядку: `vacancy_id`, `title`, `score`, `score_min`–`score_max`, `label`, `must`/`nice` (счётчики статусов), `explanation` |
| Почему такой порядок | `ranking.comparison[]` |
| «Как посчитано» | `ranking.formula` — в раскрывашке |
| Время этапов | `timings_ms` |

### Экран 3. Вакансия подробно (`reports[vacancy_id]`)

- **Вывод** — `summary`.
- **Таблица требований** — `rows[]`: `requirement`, `modality` (`must` — обязательное, `nice` — желательное), `status` / `status_ru`, `resume_evidence[]` (`fragment_id` + `quote`), `vacancy_quote`, `comment`, `computed` (расчёт стажа кодом), `evidence_type`. Порядок строк уже правильный, не пересортировывай.
- **Подсветка в резюме**: по клику на строку подсвети фрагменты `resume_evidence[].fragment_id` в тексте резюме. Текст резюме — `resume.fragments[]` (`id`, `text`, `section`), в порядке `order`.
- **Сильные стороны / пробелы / риски / сверх требований** — `strengths`, `gaps`, `risks`, `beyond_requirements`: у каждого пункта `text` и `fragment_ids`.
- **Вопросы кандидату** — `questions[]`: `text`, `why`, `kind`.
- **Рекомендация рекрутеру** — `recruiter_recommendation`; **письмо кандидату** — `candidate_message` с кнопкой «Скопировать».
- **Скачать DOCX** — ссылка на `/runs/{run_id}/report/{vacancy_id}.docx`.
- **Профиль кандидата** — `profile`: `positions[]` (должность, организация, `raw_dates`, `duration_months`), `education[]`, `skills[]`, `languages[]`, `total_experience_months`.
- **Требования вакансии** — `requirements[vacancy_id][]`: `text`, `modality`, `threshold`.
- **Что ушло наружу** — `/runs/{run_id}/outbound` в раскрывашке: доказывает жюри, что во внешний API уходят только обезличенные данные.

### Экран 4. Пакет резюме (`BatchResult`)

- `summary` — сверху.
- **Матрица** кандидат × вакансия: строки — `resumes[]` (`resume_id`, `filename`), столбцы — `vacancies[]`, ячейки — `cells[]` (`score`, `label`), цвет по `label`. Пустая ячейка — кандидат не обработан.
- **Лучшие кандидаты на вакансию** — `vacancies[].candidates` (уже упорядочены кодом) и `vacancies[].summary`.
- **Ошибки** — `errors[]` (вакансии) и `resumes[].error` (резюме не прочиталось).
- **Кандидат подробно** — `GET /runs/{resumes[].run_id}` и экраны 2–3 для него.

## 6. Правила отображения — не нарушать

Это прямо влияет на оценку жюри (критерии 4 и 5).

1. **Четыре статуса и их цвета.** Соответствует — зелёный, Частично — жёлтый, Не соответствует — красный, **Не указано — серый, не красный**: «в резюме нет сведений» ≠ «кандидат не подходит». Подписи брать из `status_ru`.
2. **Цитаты показывать как есть** из `quote` и `vacancy_quote`. Не обрезать посреди слова, не перефразировать.
3. **Балл, порядок и метки считает бэкенд.** Не пересчитывать и не сортировать по-своему. Балл показывать вместе с интервалом: «62 (от 41 до 83)».
4. Метка: подходит — зелёный, подходит с оговорками — оранжевый, не подходит — красный (`fits` / `fits_with_caveats` / `not_fit`).
5. `needs_review: true` у вердикта (в `verdicts[vacancy_id]`) — значок «проверить вручную».
6. Режим `fallback` — заметное предупреждение, что результат упрощённый.
7. Никаких своих выводов о кандидате в интерфейсе: все тексты — из API.
8. Ничего не отправлять во внешние сервисы (аналитика, шрифты из CDN с трекингом и т. п.) — в резюме персональные данные.

## 7. Как работать с репозиторием

- Код фронтенда — в папке `frontend/` в корне репозитория. В `src/`, `ui/`, `tests/` не заходи; нужна правка API — напиши владельцу репозитория.
- Ветка `f/<что-делаешь>`, PR в `main`. `git pull --rebase origin main` почаще.
- Не коммить `.env`, ключи и результаты прогонов (`data/runs/`).
- Стек — на твой выбор (React / Vue + Vite удобно: dev-сервер на :5173 уже разрешён в CORS). Адрес API — через переменную окружения фронтенда, по умолчанию `http://localhost:8000`.
- Когда будет готово, добавим фронтенд сервисом в `docker-compose.yml`, чтобы жюри поднимало всё одной командой — договоримся в PR.
- Минимум к 14.11 14:00: экраны 1–3 на примере из кейса. Пакет (экран 4) — следующим.
