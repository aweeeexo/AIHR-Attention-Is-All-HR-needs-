# План внедрения в МФТИ

Опирается на ответы заказчика и эксперта (`docs/organizers_qa.md`). Цифры заказчика помечены «по словам заказчика», наши — со ссылкой на замер.

## Исходная ситуация

- **Кто работает.** Рекрутер прогоняет резюме через систему. Нанимающий менеджер получает уже отправленное резюме с оценкой. Рекрутер может дать кандидату рекомендации.
- **Задача.** По одному резюме сразу видеть, какие из открытых вакансий подходят и почему. Так можно быстро предложить кандидату альтернативу и не потерять сильного кандидата.
- **Системы.** Отдельной ATS нет. Вакансии лежат на hh.ru и на сайте МФТИ.
- **Каналы резюме.** Больше всего откликов с hh.ru. Ещё есть поиск по базе hh.ru, сайт МФТИ, почта, рекомендации коллег и «Работа в России».
- **Объём.** Поток неравномерный. Пик приходится на 2–3 дня после публикации: до 300+ откликов в день.
- **Время сейчас, по словам заказчика:**
  - 1–3 минуты на первичный скрининг;
  - 10–20 минут на сопоставление одного кандидата с несколькими вакансиями;
  - 10–15 минут на оформление перед отправкой заказчику.

## Что меняется для рекрутера

| Шаг | Сейчас (по словам заказчика) | С AIHR |
|---|---|---|
| Вакансии | Держать в голове требования всех открытых вакансий | Один раз добавить в «Открытые вакансии» файлом или ссылкой hh.ru или сайта МФТИ |
| Сопоставление с несколькими вакансиями | 10–20 мин | Расчёт около полутора минут на резюме против трёх вакансий. Рекрутер проверяет таблицу «требование · цитата из резюме · статус» и спорные пункты с пометкой «Проверить вручную» |
| Оформление для заказчика | 10–15 мин | Кнопка «Скачать DOCX»: таблица, сильные стороны, пробелы, риски, вопросы кандидату |
| Ответ кандидату | Пишется вручную | Черновик письма. Каждое число и название в нём проверены по документам |
| Поток откликов | По одному | Пакет до 50 резюме: матрица «кандидат × вакансия» и порядок кандидатов на каждую вакансию |

Система не отсеивает кандидатов сама. «Не указано» не равно «Не соответствует»: такие пункты уходят в вопросы кандидату. Решение остаётся за рекрутером.

## Как встраивается без ATS

```
hh.ru (отклики, поиск) ─┐
сайт МФТИ, почта,       ├─ файлы DOCX / PDF / RTF / TXT ─→ AIHR (Docker во внутренней сети)
рекомендации,           │                                   ├─ реестр открытых вакансий (том vacancies)
«Работа в России»       ┘                                   ├─ рейтинг, таблица, отчёт DOCX
вакансии hh.ru и сайта ──── ссылка или файл ─────────────→  └─ журнал «что ушло наружу»
                                                                         │
                                         нанимающий менеджер ←── DOCX-отчёт
```

- **Развёртывание.** Одна команда `docker compose up --build` на сервере МФТИ. Отдельная база не нужна: вакансии и прогоны лежат в томах Docker.
- **Резюме с hh.ru.** hh.ru выгружает резюме в PDF, RTF и DOCX, все три формата AIHR читает. Рекрутер скачивает отклики и загружает их пакетом.
- **Вакансии.** Вакансию с hh.ru или сайта МФТИ добавляют ссылкой: сервер скачивает страницу и берёт текст вакансии. Резюме при этом никуда не уходит. Открытый API hh.ru без токена работодателя закрыт, поэтому берём страницу.

## Нагрузка в пик

- **Время на резюме.** Замер 14.11 без кэша, резюме против трёх вакансий, DeepSeek V4 Flash в Yandex AI Studio. Первое резюме — 87 с, вместе с разбором вакансий. Требования вакансии извлекаются один раз и потом берутся из кэша, поэтому второе резюме — 73 с. Повторный анализ тех же документов занимает секунды.
- **Параллельность.** API ведёт 2 задачи одновременно (`JOBS_WORKERS`), внутри задачи до 4 запросов к модели (`LLM_CONCURRENCY`).
- **Оценка для 300 откликов в день.** Около 75 с на резюме: в одной задаче это примерно 6 часов, при двух задачах одновременно примерно 3 часа. Поток лучше делить на пакеты по 50 резюме: пакет считается примерно час, и рекрутер разбирает готовый пакет, пока считается следующий. Это расчёт по замеру двух резюме, а не прогон на 300: столько резюме у нас нет. Для сравнения, по словам заказчика, ручное сопоставление занимает 10–20 минут на кандидата, то есть 50–100 часов на 300 откликов.
- **Если не успевать.** Можно поднять `JOBS_WORKERS` и `LLM_CONCURRENCY`, насколько позволяет лимит ключа LLM, или запустить ещё один экземпляр API.

## Персональные данные

- В LLM уходит только обезличенный текст. До отправки метками заменяются ФИО, контакты, ссылки, номера документов, дата рождения, возраст и адрес. Фразы о поле, семье и гражданстве удаляются. Перед каждым запросом guard в `llm/client.py` ещё раз проверяет текст.
- Каждый запрос наружу пишется в журнал. Рекрутер видит его в отчёте («Что ушло наружу»).
- Если внешний API недопустим, есть два варианта. Первый — локальная модель (`docker compose --profile local`). Второй — режим без LLM (`LLM_PROVIDER=none`): ни одного внешнего вызова, точность ниже (`eval/report.md`).

## Этапы

1. **Пилот, 2 недели.**
   - 1–2 направления подбора.
   - Рекрутер оценивает кандидатов как обычно и параллельно в AIHR.
   - Считаем совпадение статусов с ручной оценкой, время на кандидата и долю пунктов «Проверить вручную».
2. **Все открытые вакансии в реестре.**
   - Вакансии хранятся с адресом источника.
   - Закрытая вакансия удаляется одной кнопкой.
3. **Почта для откликов.**
   - Вложения писем на ящик подбора ложатся в пакет на анализ.
   - Новая интеграция, без изменения ядра.
4. **hh.ru API работодателя.**
   - С токеном работодателя МФТИ отклики и вакансии забираются без ручной выгрузки.
   - Нужен доступ работодателя к API hh.ru: это решает МФТИ.

## Метрики пилота

- **Время.** От получения резюме до отправки заказчику; сравниваем с 20–35 минутами (по словам заказчика).
- **Совпадение статусов** с решением рекрутера. На нашем эталоне 84%, на отложенном наборе других профессий 96% (`eval/report.md`, D57).
- **Ложные «Не соответствует»** там, где в резюме просто нет сведений. Цель — 0, на эталоне 0.
- **Альтернативные вакансии.** Доля кандидатов, которым предложили другую вакансию из рейтинга.

## Риски

| Риск | Что делаем |
|---|---|
| Модель ошибается в спорных пунктах | Цитату подставляет код, а не модель. Спорные пункты помечены «Проверить вручную». Стаж и пороги считает код |
| Ответы модели меняются от запуска к запуску | Temperature 0 и кэш по хэшу запроса. Разброс от переспроса ±5 п. п. на эталоне (D57) |
| Страница вакансии не скачивается | Понятная ошибка и загрузка файлом. Остальное работает без сети |
| Внешний API недоступен | Режим без LLM и локальная модель; битый документ не роняет прогон |
