## 3. Вход — загрузка документов (`src/aihr/ingest/`, критерий 5)

**Что не умеет сейчас** (кандидаты на доработку — выбрать 1–2):

## 4. Режим без LLM (`src/aihr/fallback/`, критерии 2 и 5)

**Зачем.** Если у жюри не будет ключа LLM или провайдер упадёт, система всё равно должна выдать рейтинг и таблицу — это `LLM_PROVIDER=none`. Задача целиком — `docs/tasks/T11_fallback.md`, решение — D9.

**Что уже есть.** `fallback/requirements.py` — требования по разделам вакансии, модальность по ролям и маркерам, пороги лет/образования/языка регулярками. `fallback/profile.py` — места работы по датам, образование, навыки, языки. `fallback/matching.py` — покрытие слов требования лучшими фрагментами (BM25 + синонимы + эмбеддинги): ≥ 0.6 — «Соответствует», 0.34–0.6 — «Частично», пороги стажа — `match/rules.py`.

**Текущие цифры** (`eval/report.md`, строка «Без LLM»): полнота требований 86%, macro-F1 статусов 0.50, точность 73%, лучшая вакансия 3 из 4, **«Не соответствует» вместо «Не указано» — 0**. С LLM: macro-F1 0.77, точность 86%.

**Главное слабое место** — по матрице ошибок 20 «Соответствует» и 14 «Частично» из эталона режим ставит в «Не указано»: не находит подтверждение, которое есть другими словами.

**Идеи** (выбрать 1–2):
- больше канонов и написаний в `data/synonyms.yaml` (это общий файл — согласуй с Александром; только общие термины, не слова из вакансий кейса);
- учитывать раздел «О себе» и сопроводительное письмо как подтверждение навыков (сейчас часть подтверждений лежит там);
- точнее пороги покрытия 0.6 / 0.34 — подбирать на **своих** тестовых резюме, не на кейсе;
- лучшее деление перечислений в требованиях («Excel, Google Sheets» → два требования).

**Как проверить:** `uv run poe eval` пересчитает `eval/report.md`; смотри строку «Без LLM» и её матрицу ошибок. Без ключа LLM строки с LLM будут «не посчитано» — это нормально, **не коммить `eval/report.md`, если в нём пропали строки с LLM** (скажи Александру, он пересчитает со своим ключом). Плюс `uv run poe test` (`tests/test_fallback.py`) и `LLM_PROVIDER=none uv run aihr demo`.

**Нельзя:** ставить «Не соответствует» без факта, который противоречит требованию (это главная метрика надёжности — должно остаться **0**); писать в код слова из трёх вакансий кейса (`uv run poe check-leak`); подгонять пороги под конкретный документ кейса — жюри это проверяет («нет ручных настроек под конкретный документ»).

## 5. Вторая разметка эталона (критерий 4, честность метрик)

**Зачем.** Все наши метрики считаются по эталону, который размечал один человек. Независимая вторая разметка даёт **согласие разметчиков (каппу Коэна)** — без неё жюри может сказать «вы сами себе поставили оценку».

**Важно: размечай независимо.** Не открывай `eval/golden/verdicts_*.json`, `eval/report.md`, результаты прогонов (`data/runs/`) и интерфейс с ответами системы для этих пар, пока не закончишь.

**Какие пары** (≈16 требований каждая, 1–2 часа на все три):

| Пара | Резюме | Вакансия | Чем интересна |
|---|---|---|---|
| R2 × V1 | Петров (разработчик) | Вакансия 1 | много «Соответствует» и «Частично» |
| R4 × V2 | Петрова (бухгалтер) | Вакансия 2 | смежный опыт, «Частично» |
| R1 × V3 | Иванов (ассистент, аналитик) | Вакансия 3 | личные качества, косвенные подтверждения |

**Как:**

```bash
uv run python scripts/label_pair.py R2 V1 --template   # покажет требования и резюме, создаст шаблон
# заполни eval/golden/second/verdicts_R2_V1.json: status, fragment_ids, evidence_type, annotator
uv run python eval/agreement.py                         # согласие с первой разметкой и список расхождений
```

**Рубрика** (полностью — README «Правила оценки» и `docs/tasks/T07_matching.md`):

- `match` — требование подтверждено фрагментом резюме целиком;
- `partial` — подтверждено частично: меньше срок, ниже уровень, смежный навык того же класса;
- `mismatch` — **только** если в резюме есть факт, который противоречит требованию (например, образование ниже требуемого);
- `not_stated` — в резюме об этом ничего нет. Молчание ≠ «нет».
- Личные качества («коммуникабельность», «ответственность») — `match` только при прямом факте о себе; смежные факты («согласовывал правки») не считаются → `not_stated` (D43).
- `fragment_ids` — номера фрагментов резюме (`R12`), на которые опирается вывод; для `not_stated` — `[]`.
- `evidence_type` — `direct` (прямо написано), `indirect` (следует из другого факта), `adjacent` (смежный навык); для `not_stated` — `null`.

**Результат:** ветка `t/second-labels` с тремя файлами в `eval/golden/second/` и выводом `eval/agreement.py`. Расхождения не исправляй под первую разметку — их обсудим, по ним видно, где рубрика неоднозначна.
