# Решения команды

Принятые решения не меняем без обсуждения обоих. Новое решение — новая строка с номером. Отменённое помечаем «отменено, см. Dn», а не удаляем.

## Принятые

| № | Решение | Почему |
|---|---|---|
| D1 | Python 3.12, uv, FastAPI, Streamlit, Docker Compose | Все нужные NLP-библиотеки есть в Python. uv даёт lock-файл и быструю сборку. Compose нужен по критерию 6 для многокомпонентного решения |
| D2 | Порядок работ: каркас в Docker → извлечение → сопоставление с цитатами → балл и рейтинг → отчёт → плохие файлы → README и примеры → доп. фичи | Сначала закрываем технические 100 баллов, по ним отбирают в топ-3 |
| D3 | **Обязанности из вакансии превращаем в пожелания (nice), не в обязательные требования.** `kind=duty`, `modality=nice`, никогда не блокируют | Не все кандидаты пишут, что конкретно делали. Если считать обязанности обязательными, отсеем много подходящих людей |
| D4 | **Нокаута нет.** Обязательное требование со статусом «Не соответствует» помечается как блокирующий пробел (`blocking_gaps`) и не даёт метку «подходит», но кандидат остаётся в рейтинге со своим баллом | Кандидат с сильным набором навыков и одним несоответствием может подойти. Решение принимает рекрутер |
| D5 | **«Не указано» входит в формулу с нейтральным значением u = 0.5.** Дополнительно показываем интервал: u = 0 (минимум) и u = 1 (максимум). Исключать из формулы нельзя | Если исключить, пустое резюме с одним совпадением получит 100%. Интервал честно показывает неопределённость |
| D6 | **Сопоставление — гибрид (вариант C).** Проход A: все требования вакансии одним вызовом. Проход B: отдельный вызов с поиском доказательств только для спорных требований | Лучшее соотношение качества и цены. Короткие резюме не требуют поиска, сложные случаи получают отдельное внимание |
| D7 | **Направление сравнения.** Основное — от вакансии к резюме (позиция HR): для каждого требования ищем подтверждение, строго. Из него строятся таблица, статусы, балл и рейтинг. Вспомогательное — от резюме к вакансии (позиция кандидата): какие факты резюме покрывают требования и какой опыт остался за рамками требований. Оно идёт только в сильные стороны и рекомендации и **никогда не влияет на балл** | Кейс требует строгую таблицу по требованиям и объяснимый рейтинг. Позиция кандидата добавляет «что ещё он умеет», но не должна размывать строгость |
| D8 | LLM не пишет цитаты. Модель возвращает `fragment_ids`, текст подставляет код | Выдумать цитату становится невозможно (deterministic quoting) |
| D9 | Нет проверенного фрагмента → статус «Не указано», что бы ни ответила модель. «Не соответствует» требует фрагмент, который противоречит требованию | Прямо закрывает 5 баллов критерия 5: отсутствие сведений не трактуется как отсутствие навыка |
| D10 | Единственная точка выхода наружу — `llm/client.py` с guard и журналом исходящих запросов | Ограничение кейса по данным можно проверить, а не принять на веру |
| D11 | Балл и рейтинг считает код по формуле из `score/`. LLM не участвует в упорядочивании | Объяснимость и единая логика (критерий 3) |
| D12 | В коде и промптах нет терминов из вакансий кейса. Few-shot примеры — из других профессий | 3 балла за «единую логику без ручной настройки» и работа на новых документах (критерий 5) |
| D13 | Числовые пороги (стаж, уровень образования, уровень языка) проверяет код | Модели ошибаются в арифметике дат |
| D14 | Синонимы в три слоя: словарь (+ расширение через LLM для незнакомых терминов, с кэшем), эмбеддинги, суждение LLM | Без этого всё поломается на новых формулировках |
| D15 | Тип доказательства: прямое, косвенное, смежное. Косвенное обязательно содержит цепочку вывода со ссылками на фрагменты. Смежное даёт максимум «Частично» | Учёт контекста (критерий 2) и проверяемость вывода |
| D16 | Названия работодателей и вузов не маскируем по умолчанию | Нужны для оценки опыта. Слепой режим — доп. фича позже |
| D17 | Temperature 0, кэш по хэшу (модель + prompt_id + версия промпта + текст), закреплённые версии | Повторный прогон на тех же файлах даёт тот же результат |
| D18 | **Отменено 12.11, см. D27.** ~~Соло-режим, пока не подключился тиммейт.~~ Все задачи — одна очередь в порядке из `docs/tasks/README.md`. Роли A и B не делим, владельцы модулей не действуют. Контракты можно менять, но в том же коммите обновить `docs/contracts.md`, `CONTRACTS_VERSION` и тесты | Без второго человека деление на роли только тормозит. Файлы ролей оставлены на потом |
| D19 | **Разработка на Windows.** Python 3.12 через uv (не 3.14 из PyCharm). Команды — задачи poethepoet (`uv run poe <задача>`), Makefile — обёртка над ними для Linux и жюри. `.gitattributes` с `eol=lf`, `PYTHONUTF8=1`. torch ставится из CPU-индекса | На Windows нет make. CRLF ломает скрипты в Linux-контейнере. CUDA-сборка torch добавила бы гигабайты к образу без пользы |
| D20 | **LLM только по API.** Профиль `local` в Compose делаем, но проверяем на одной паре | На Ryzen 7 7840HS без NVIDIA модель 7–8B даёт порядка 10 токенов в секунду, а полный прогон кейса — около 100 тыс. выходных токенов, то есть часы |
| D21 | **Makefile: цели с Docker (`up`, `down`, `demo`, `test-docker`) вызывают `docker compose` / `docker` напрямую**, остальные — `uv run poe`. Тесты в Linux-контейнере — отдельная стадия `test` в Dockerfile (`make test-docker`) | У жюри может не быть uv: запуск по README не должен от него зависеть |
| D22 | **Образ:** `python:3.12.16-slim-trixie` и `uv 0.12.21`, закреплены тегами. Эмбеддинги в образ по умолчанию не ставим (`WITH_EMBEDDINGS=0`), включаются аргументом сборки | Быстрая сборка, пока не замерено время с torch (открытый вопрос про размер модели) |
| D23 | **setuptools закреплён на 80.10.2** | pymorphy2 внутри Natasha 1.6.0 импортирует `pkg_resources`, которого нет в setuptools 81+. Без него `MorphVocab` падает |
| D24 | **Сбой после загрузки документа** (шаг вакансии упал, отчёт не собрался) идёт в `MatchResult.warnings`, вакансия выпадает из рейтинга, остальные считаются. `IngestError` — только для ошибок загрузки и `E_NO_REQUIREMENTS`. **LLMUnavailable на любом шаге переводит весь прогон в режим без LLM** с предупреждением | В `IngestErrorCode` нет кодов для сбоев обработки. Пересмотреть в T03/T11: возможно, нужен код вроде `E_PROCESSING` (изменение контракта) |
| D25 | **Папка как набор вакансий:** берём docx, pdf, txt, кроме файлов со словами «резюме», «resume», «cv» в имени. По этому же признаку `/match/example` и `aihr demo` делят `data/case/` на резюме и вакансии | В папке кейса резюме и вакансии лежат вместе, а команда из CLAUDE.md передаёт её целиком |
| D26 | **Временный провайдер для разработки — прокси [FreeDeepseekAPI](https://github.com/ForgetMeAI/FreeDeepseekAPI)** (веб-чат DeepSeek, модель DeepSeek-V4.1-Flash, alias `deepseek-chat`). Лежит рядом с проектом в `../FreeDeepseekAPI`, слушает `localhost:9655`, в `.env`: `LLM_BASE_URL=http://localhost:9655/v1`, `LLM_MODEL=deepseek-chat`. Только для локальной разработки, не для жюри. Постоянного провайдера выбирает пользователь 13.11 | Проверено 12.11: JSON по схеме с первой попытки, номера фрагментов только существующие, 2–5 с на вызов, 2 параллельных запроса работают, повтор дал тот же ответ. Прокси игнорирует `temperature` и `response_format` → воспроизводимость только через кэш (T03). Данные уходят на серверы DeepSeek → резюме кейса только после T02 |
| D27 | **Работаем вдвоём с 12.11.** Владелец репозитория — роль B (платформа), тиммейт на втором аккаунте Claude — роль A (ML-ядро). Модули — по `docs/roles/`. Ветки `a/…` и `b/…`, PR в `main`. Контракты — только по согласию обоих. У каждого свой доступ к LLM (свой аккаунт DeepSeek через FreeDeepseekAPI, D26) | ML-ядро (критерии 1, 2, 4) не ждёт платформу (критерии 3, 5, 6). Разделение по модулям убирает конфликты в одних файлах |
| D28 | **Загрузка (T01):** поддерживаем docx, pdf, rtf (`striprtf`) и txt; тип — по содержимому. Заголовки разделов — словарь структуры документа отдельно для резюме и для вакансий: в вакансии «Образование: высшее» — строка требований, а не раздел. «Заголовок: N лет» — заголовок раздела, «Заголовок: текст» — роль только для этой строки. Меньше 50 символов текста → `E_NO_TEXT`, меньше 300 → предупреждение | Без раздельных словарей строки вакансии «Опыт работы от 1 года» и «Образование: …» ломали роли. Словарь не содержит предметных слов (D12) |
| D29 | **Маскирование (T02):** слово из имени файла или первой строки считается ФИО, только если pymorphy знает его как имя, фамилию или отчество. Шаблон склонений чувствителен к регистру. Чужие имена маскируем, только если NER нашёл не меньше двух слов. Город маскируем только в контактах резюме, в вакансиях — нет. Текст ошибки валидации для повторного запроса — без ссылок pydantic | Иначе «Менеджер» из имени файла, слово «роман» и названия компаний, которые Natasha принимает за людей, маскировались бы, а guard блокировал бы повтор из-за ссылки в тексте ошибки. Город в вакансии — открытые данные и нужен для сопоставления |
| D30 | **LLM-клиент (T03):** `json_schema` отправляем со `strict: false`, схема всегда дублируется текстом в системном сообщении, `seed` не передаём. Кэш включён по умолчанию (`LLM_CACHE=1`) | `strict: true` не принимает схемы pydantic с необязательными полями. Прокси веб-чатов игнорируют `response_format`. Неизвестный параметр `seed` часть серверов отклоняет с 400, и режим auto принял бы это за отказ от json_schema. Кэш — основа воспроизводимости: temperature 0 соблюдается не везде |
| D31 | **Стаж (T05-B):** длительность — разница месяцев (03.2021–06.2024 = 3 г. 3 мес., как в контракте), минимум 1 месяц. Год без месяца — середина года (июль), а не январь–декабрь, и флаг «≈». Одиночный год «2017» — работа в пределах года (12 мес.); «по настоящее время» — только при явном маркере или «с …» | Январь–декабрь завышал бы стаж до года: «2019–2021» давало бы 3 года и ложно проходило порог «от 3 лет». Середина года совпадает с прочтением рекрутера и с примером из T05 (2019–2021 и 2020–2022 → 36 мес.) |
| D32 | ~~Заменено D42.~~ **Эмбеддинги в образе по умолчанию выключены** (`WITH_EMBEDDINGS=0`), включаются аргументом сборки. Модель `intfloat/multilingual-e5-small` скачивается при сборке, в рантайме сеть не нужна. `Retriever(..., embeddings=False)` — явный режим только BM25 | Образ для жюри в 3 раза меньше и собирается в 2 раза быстрее. Прирост качества пока не доказан на золотом наборе (см. открытый вопрос) |
| D33 | **Требования (T04):** модальность решает код — маркер ищется в той части фразы (по запятым, «;», «и»), к которой относится требование, плюс строчный заголовок «Будет плюсом:»; при «будет плюсом» и «обязательно» в одной части побеждает «будет плюсом». Альтернативы без «или», «/», «одно из» — это перечисление, делим на атомарные. Вакансии маскируются раньше резюме | Во фразе «нужны права C, знание города желательно» маркер по всему фрагменту делал оба требования желательными. Модель кладёт «A, B и C» в alternatives. Порядок маскирования делает промпт извлечения независимым от кандидата — работает кэш |
| D34 | **Синонимы (T06-A):** словарь собран вручную по общему списку областей (LLM для генерации не было), омонимы — отдельный список, `canonicalize` для них даёт None. Канонические маркеры `=канон` добавляются к токенам поиска и покрытия, а не заменяют слова | Ручной словарь проверен глазами целиком. Маркеры поверх слов не ломают точные совпадения и дают совпадение «JS» = «JavaScript», «1С» = «1C» |
| D35 | **«Ни одна вакансия прямо не подходит» — валидный итог (подтверждено 12.11).** Если у всех вакансий метка «не подходит», рейтинг и отчёт прямо это говорят, обосновывают непокрытыми обязательными требованиями с фрагментами и показывают вакансии, куда кандидат мог бы подойти косвенно: смежные навыки, косвенный опыт, частичные совпадения — с тем, чего не хватает. Текст — в `Ranking.summary` (контракт v2) | Организаторы: «ни одна не подходит» допустимо с обоснованием; рекрутеру нужно понимать, какие альтернативы предложить кандидату |
| D36 | **Читатель отчёта — нанимающий менеджер (подтверждено 12.11).** Сверху — короткий вывод без HR-терминов (`Report.summary`, контракт v2), затем таблица, сильные стороны и риски. Рекомендация рекрутеру и вопросы кандидату — отдельный блок для рекрутера | Организаторы: менеджеру приходит резюме с оценкой, рекрутер на её основе даёт рекомендации |
| D37 | **Экспорт отчёта в DOCX — в приоритете (подтверждено 12.11).** Делаем раньше эмбеддингов и косвенных выводов (T07, шаг 7); в порядке «что режем» экспорт больше не первый. PDF — если останется время | Оформление перед отправкой заказчику занимает у рекрутера 10–15 мин — экспорт сокращает этот шаг напрямую. python-docx уже в зависимостях |
| D38 | **Пакетная загрузка резюме — сделано (12.11, после основной работы).** Несколько резюме × вакансии: `run_batch` поверх `pipeline.run` (каждый кандидат — полный прогон со своим отчётом и журналом), `BatchResult` в контрактах v3, `POST /match/batch`, `/match/batch/example`, `GET /batches/{id}`, `aihr batch`, вкладка «Пакет резюме» в UI. Интеграцию с ATS не делаем | Вход кейса — одно резюме; пик 300+ откликов в день — аргумент для доп. фичи. Отдельной ATS у организаторов нет |
| D39 | **Пока нет API — провайдер `LLM_PROVIDER=replay` (12.11).** Клиент после guard кладёт запрос в `data/llm_replay/queue/`, ответ берёт из `answers/` (`src/aihr/llm/replay.py`). | D40 | **«Почти вровень»: разница баллов меньше `close_margin` (3) — объяснение места и итог по вакансиям говорят, что порядок ненадёжен и выбор — по таблицам требований.** Порядок рейтинга не меняется, порог в `config/scoring.yaml` | Проверка весов на вердиктах LLM (12.11, `scripts/score_stability.py`): у 2 резюме из 4 порядок меняется при must = 4 или частично = 0.4/0.6 — именно там, где баллы различаются на 0,6–1,4. | D41 | **«Подходит с оговорками» — только при достаточных данных** (согласовано 12.11, уточняет D5 и T08). Нужно: балл ≥ 45 и подтверждена (соответствует или частично) хотя бы половина обязательных — `min_confirmed: 0.5` в `config/scoring.yaml`, — либо нижняя граница интервала ≥ 45. | D42 | **Эмбеддинги включены по умолчанию (12.11, заменяет D32): гибридный поиск доказательств BM25 + синонимы + `intfloat/multilingual-e5-small` на CPU, слияние RRF.** `WITH_EMBEDDINGS=1` в Dockerfile, Compose и `.env.example`; `0` — сборка только с BM25. Замер на золотом наборе: recall@8 с фильтром разделов — 80% (BM25) и 83% (гибрид); без фильтра, с бонусом — 85% и 93% при цели 90%. **Поправка 12.11:** эти цифры считались только по вакансии 1 (в `eval` все вакансии грузились с номером V1 и пункты V2, V3 выпадали).
