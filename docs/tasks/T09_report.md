# T09. Отчёт рекрутеру

**Владелец:** A · **Зависит от:** T07, T08 · **Критерии:** 4 (12 баллов), пункты 4–6 ожидаемого результата кейса

## Цель

Рекрутер видит по каждой вакансии таблицу требований с цитатами из обоих документов, сильные стороны, пробелы, риски, вопросы кандидату и рекомендацию. Отчёт собирается из уже проверенных вердиктов. Генеративный текст проходит проверку сущностей, выдуманных фактов нет.

Команда отметила этот блок как место, где стоит повозиться.

## Принцип

Сначала доказательства, потом текст. Всё, что можно собрать кодом из вердиктов, собирается кодом. LLM используется только для формулировок и всегда получает на вход проверенные факты, а не резюме целиком.

## Шаги

### 1. Таблица требований (5 баллов за связь с фрагментами)

`RequirementRow` на каждое требование: формулировка, must / nice, **цитата из вакансии** (по `source_fragment_ids`), **цитаты из резюме** (из `Verdict.evidence`), статус по-русски, тип доказательства, комментарий, расчёт (`computed`). Обе цитаты подставляет код.

Порядок строк: сначала обязательные, внутри — «Не соответствует», «Частично», «Не указано», «Соответствует». Рекрутер сначала видит, что требует внимания.

### 2. Сильные стороны (собирает код)

- Обязательные требования со статусом «Соответствует», по убыванию веса.
- Превышение порога: факт ≥ 1.5 × порог («5 лет при требуемых 2»).
- Достижения с числами из мест работы, относящихся к требованиям.
- `beyond_requirements` из позиции кандидата (T07, шаг 9) — отдельным подблоком «Сверх требований».

Каждый пункт — `Point` со ссылками на требования и фрагменты.

### 3. Пробелы (собирает код)

Обязательные «Не соответствует» и «Частично» с полем `missing`. Для смежных навыков пометка «закрывается обучением». Блокирующие пробелы (D4) — первыми.

### 4. Риски (собирает код, нейтральные формулировки)

- Обязательное требование со статусом «Не указано».
- Требуемый навык есть только в списке навыков, без подтверждения опытом.
- Навык не использовался больше 5 лет (`last_used_year`).
- Перерыв в работе больше 6 месяцев (`gaps_months`).
- Расхождение проходов A и B (`needs_review`).
- Косвенное доказательство обязательного требования.

Формулировка всегда «стоит уточнить …». Никаких оценок личности, возраста, пола, семейного положения.

### 5. Вопросы кандидату

- Источник: каждое обязательное «Не указано», «Частично», навык `listed_only` из требований, требования `verifiable=false`.
- Два типа: фактический («Работали ли вы с …? Сколько лет?») и поведенческий («Расскажите о последнем случае, когда вы …»).
- Приоритет по весу требования, итого 3–7 вопросов.
- У каждого вопроса — `why`: на какое требование и какой пробел он отвечает.
- Генерирует LLM (`report/prompts/questions.md`) по структуре: требование + статус + `missing`. Без доступа к резюме — ему не нужно.

### 6. Рекомендация рекрутеру

Основа — шаблон из метки и чисел: «Подходит с оговорками: 5 из 6 обязательных требований, не подтверждён опыт …. Следующий шаг: короткий звонок для уточнения 2 вопросов». Плюс следующий шаг по метке: пригласить на интервью, уточнить по телефону, предложить другую вакансию из рейтинга (если у неё метка лучше). LLM может переписать шаблон глаже — только с проверкой из шага 8.

### 7. Письмо кандидату

Черновик для рекрутера, не отправляется автоматически. Два варианта по метке:

- приглашение с 2–3 уточняющими вопросами;
- вежливый отказ с обратной связью: какие требования не подтверждены и что можно предложить вместо (другая вакансия из рейтинга, если подходит).

Только факты из вердиктов. Без оценок кандидата как человека.

### 8. Проверка сущностей (3 балла за отсутствие выдуманных фактов)

Для каждого сгенерированного текста (вопросы, рекомендация, письмо):

1. Код извлекает сущности: числа, даты, годы, слова латиницей, названия с заглавной буквы, названия навыков по словарю синонимов.
2. Каждая сущность должна найтись в фактах, переданных в генерацию (вердикты, требования, профиль).
3. Не нашлась → повторная генерация с указанием на ошибку. Опять не нашлась → откат к шаблону.
4. Счётчики в `VerificationStats`: всего цитат, проверенных цитат, всего сущностей, непроверенных. На выходе должно быть `quotes_verified == quotes_total` и `generated_entities_unverified == 0`.

### 8а. Вывод для нанимающего менеджера (D36)

`Report.summary` — 2–3 предложения сверху отчёта без HR-терминов: метка, сколько обязательных требований подтверждено, главное, что не подтверждено, и главная сильная сторона. Собирается шаблоном. Рекомендация рекрутеру и вопросы кандидату — отдельный блок для рекрутера.

### 8б. «Почему ничего не подошло» (D35)

Если у всех вакансий метка «не подходит», в выводе и в письме кандидату — прямо «не подходит» с обоснованием и вакансии, куда кандидат мог бы подойти косвенно (из `Ranking.summary`, T08).

### 8в. Экспорт в DOCX (D37)

Отчёт по вакансии — файл .docx: вывод для менеджера, таблица требований с цитатами из вакансии и резюме, сильные стороны, пробелы, риски; отдельным разделом — блок для рекрутера (рекомендация, вопросы, черновик письма). Скачивание в UI и `GET /runs/{run_id}/report/{vacancy_id}.docx`. PDF — если останется время.

### 9. Метки происхождения

В UI и JSON видно, что откуда: цитаты из документов (отдельный стиль), расчёты кода, сгенерированный текст. Рекрутер отличает доказательство от пересказа.

## Тесты

- Резюме без образования и без дат → в письме и рекомендации нет вуза, стажа, лет.
- Подложенный в генерацию вымышленный факт ловится проверкой сущностей.
- Каждый `Point` и `Question` ссылается на существующие требования и фрагменты.
- Нет оценочных формулировок о личности (простой словарь стоп-фраз).

## Критерии готовности

- [ ] Для 12 пар кейса отчёт полный: таблица, сильные стороны, пробелы, риски, вопросы, рекомендация, письмо.
- [ ] `VerificationStats` чистый на всех 12 парах.
- [ ] Рекрутер (любой из нас в роли) проверяет любой вывод одним кликом до цитаты.
