# T08. Балл и рейтинг

**Владелец:** B · **Зависит от:** контракты (можно начинать сразу на заглушках вердиктов) · **Критерии:** 3 (16 баллов)

## Цель

Вакансии упорядочены по рассчитанным показателям. Причина места каждой объяснена числами. Одна формула и один конфиг для всех вакансий, никаких настроек под конкретный документ.

## Формула

```latex
S = 100 \cdot \frac{\sum_i w_i \, v_i}{\sum_i w_i}, \qquad v_i = \begin{cases} 1 & \text{соответствует} \\ p_i & \text{частично} \\ 0 & \text{не соответствует} \\ u & \text{не указано} \end{cases}
```

`config/scoring.yaml`:

```yaml
weights:
  must: 3
  nice: 1          # обязанности (duty) идут как nice — D3
partial_default: 0.5   # p, если у требования нет числового порога
unknown_value: 0.5     # u, нейтрально — D5
labels:
  fits:              { min_score: 70, max_blocking_gaps: 0 }
  fits_with_caveats: { min_score: 45 }
  # остальное — not_fit
```

- `p_i` = `partial_value` из правила (например, 1.5 года из 3 = 0.5), иначе `partial_default`.
- `score` при u = 0.5; `score_min` при u = 0; `score_max` при u = 1 (D5). «Не указано» из формулы **не исключаем**: иначе пустое резюме с одним совпадением получит 100%.
- `blocking_gaps` — обязательные требования со статусом «Не соответствует». **Нокаута нет (D4):** вакансия остаётся в рейтинге со своим баллом, но метка не может быть «подходит». Кандидат с сильным набором навыков и одним несоответствием может подойти, решает рекрутер.
- Пороги меток — начальные значения. A калибрует их на золотом наборе (T10), итоговые значения записываем в `docs/decisions.md`.

## Шаги

1. `score_vacancy(vacancy, reqs, verdicts) -> VacancyScore`: балл, интервал, счётчики по must и nice, блокирующие пробелы, метка.
2. **Вклад требований.** Для каждого требования: вклад = `w_i · v_i`, потеря = `w_i · (1 − v_i)`. `top_plus` — 3 требования с наибольшим вкладом, `top_minus` — 3 с наибольшей потерей.
3. **Объяснение шаблоном, без LLM:** «Закрыто 5 из 6 обязательных и 2 из 4 желательных. Не указано 1 требование, поэтому балл от 61 до 74. Сильнее всего добавили: …. Больше всего потеряно на: ….»
4. `rank(scores) -> Ranking`: сортировка по `score` по убыванию. При равенстве — доля закрытых обязательных, затем меньше «не указано», затем `vacancy_id`.
5. **Сравнение соседей шаблоном:** «V1 выше V3 на 31 пункт: в V3 не подтверждены 3 обязательных требования (…)».
6. `Ranking.formula` — формула и веса из конфига человеческим текстом. Показывается в UI по кнопке «Как посчитано».
7. **Крайние случаи:** у вакансии нет обязательных требований → считаем по желательным, пишем предупреждение. Требований нет совсем → `E_NO_REQUIREMENTS`, вакансия не участвует в рейтинге, причина видна. Все требования «не указано» → балл 50, интервал 0–100, метка «с оговорками», предупреждение «мало данных для вывода».

## Проверка устойчивости (если останется время)

Меняем веса must на 2 и 4, `partial_default` на 0.4 и 0.6. Записываем, меняется ли порядок вакансий для 4 резюме кейса. Это готовый ответ жюри на вопрос «почему веса именно такие».

## Тесты

- Ручной расчёт на маленьком примере совпадает с кодом.
- Интервал: без «не указано» `score_min = score = score_max`.
- Обязательное «не соответствует» → метка не `fits` при любом балле.
- Пустое резюме против вакансии → балл 50, а не 100 и не 0.
- `grep` по `score/` не находит названий вакансий и условий под конкретный документ.

## Критерии готовности

- [ ] Рейтинг для 4 резюме кейса посчитан, объяснение каждого места читается без формулы.
- [ ] Лучшая вакансия для каждого резюме совпадает с ручной разметкой (T10).
- [ ] Кнопка «Как посчитано» в UI показывает формулу и веса.
