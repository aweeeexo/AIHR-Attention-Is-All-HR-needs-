# T04. Требования вакансии

**Владелец:** A · **Зависит от:** T00 (заглушка клиента), T01 (роли разделов) · **Критерии:** 1 (8 баллов: требования, обязательные и желательные)

## Цель

Из любой вакансии получить список атомарных требований: у каждого есть тип, must / nice с обоснованием, порог (если есть) и ссылка на фрагменты вакансии. Ни одна строка разделов требований, обязанностей и «будет плюсом» не теряется.

Все пункты этой задачи команда отметила как обязательные.

## Вход и выход

`extract_requirements(vacancy: Document, llm: LLMClient) -> list[Requirement]` — см. `docs/contracts.md`.

## Шаги

### 1. Атомаризация (обязательно)

«Знание AutoCAD, Revit и ГОСТ на проектную документацию» → три требования, каждое проверяется отдельно. Так у каждого навыка будет честный статус вместо одного «частично» на всё.

Исключение — альтернативы. «A или B», «A / B», «одного из: A, B, C» → одно требование с `alternatives=[A, B, C]`. Выполнено, если подтверждена любая альтернатива.

### 2. Модальность по маркерам (обязательно)

Порядок решения, первое сработавшее правило побеждает:

1. **Маркер во фрагменте** (ищет код по словарю, а не модель):
   - must: «обязательно», «необходимо», «требуется», «не менее», «от N лет», «обязательное условие», «must»;
   - nice: «желательно», «будет плюсом», «приветствуется», «преимуществом будет», «как плюс», «nice to have».
2. **Роль раздела** из T01: `requirements` → must, `nice_to_have` → nice, `duties` → nice (решение D3, см. шаг 3).
3. **Мнение модели** с обоснованием — только если ни маркера, ни роли раздела нет (вакансия сплошным текстом).

В `modality_marker` пишем найденный маркер, в `modality_reason` — короткое объяснение: «маркер "будет плюсом"», «раздел "Требования" без маркера → must», «раздел "Обязанности" → пожелание (D3)». **Правило «нет маркера в разделе требований → must» описываем в README.**

### 3. Обязанности как пожелания (D3)

Из раздела «Обязанности» извлекаем неявные требования: «планирование графика поставок» → «опыт планирования поставок», `kind=duty`, `modality=nice`. Они никогда не обязательные и никогда не блокируют: не все кандидаты пишут, что конкретно делали, и иначе мы отсеем много подходящих людей.

Одна обязанность → одно требование. Не дробим мелко: «подготовка отчётов для руководства» — одно требование, а не «отчёты» и «руководство».

### 4. Пороги

- «опыт от 3 лет в складской логистике» → `kind=experience`, `threshold={kind: years, value: "3", subject: "складская логистика"}`.

Примеры в этом файле намеренно из других профессий: их можно переносить в промпт, термины вакансий кейса — нельзя (D12).
- «высшее образование» → `threshold={kind: education_level, value: "higher"}`. Значения: `secondary`, `vocational`, `higher`, `master`, `phd`.
- «английский не ниже B2» / «английский — разговорный» → `threshold={kind: language_level, value: "B2"}`. Перевод словесных уровней в CEFR делает код (`normalize/levels.py`, T05-B).

Проверяет пороги код (T07, шаг 4), модель только извлекает.

### 5. Проверяемость

`verifiable=false` для требований, которые по резюме проверить нельзя: «стрессоустойчивость», «внимательность», «готовность к командировкам». Они остаются в таблице, почти всегда получают «Не указано» и превращаются в вопросы для интервью (T09).

### 6. Промпт

`src/aihr/extract/prompts/requirements.md`. Вход: фрагменты вакансии `[V2.5] текст` с ролями разделов, только `masked_text`. Выход: схема `list[Requirement]` без `id` и `vacancy_id` (их ставит код).

В промпте:

- правила атомаризации и альтернатив с примерами;
- поле `modality_reason` перед `modality`;
- каждое требование обязано ссылаться на `source_fragment_ids`;
- раздел «Условия» (зарплата, график, офис) не извлекаем — это не требования к кандидату;
- 2 примера из других профессий (логист, медсестра), без терминов вакансий кейса (D12).

### 7. Постобработка кодом

1. Все `source_fragment_ids` существуют, иначе требование отбрасываем с предупреждением.
2. Модальность перепроверяется правилами шага 2. Если код и модель расходятся, побеждает маркер или роль раздела. Расхождение пишем в лог.
3. `canonical_terms` через `canonicalize()` из слоя синонимов (T06-A).
4. Дубли склеиваем: одинаковые `canonical_terms` и тип, или требование и обязанность про одно и то же. Остаётся более строгая модальность, `source_fragment_ids` объединяются.
5. `id = V{n}.req{m}` по порядку появления.

### 8. Проверка покрытия кодом (обязательно)

Каждый фрагмент разделов `requirements`, `nice_to_have`, `duties` должен быть источником хотя бы одного требования. Непокрытые фрагменты → повторный вызов модели только на них. Остались непокрытыми → предупреждение в `Document.warnings` с id фрагментов. Это ловит пропущенные требования без второй модели.

### 9. Кэш

Вакансия разбирается один раз, а не на каждое резюме. Кэш по хэшу «текст документа + версия промпта» уже есть в клиенте (T03). Проверить, что при прогоне 4 резюме × 3 вакансии вызовов извлечения ровно 3.

## Критерии готовности

- [ ] На 3 вакансиях кейса: полнота требований ≥ 90% и верная модальность ≥ 90% против ручного списка (`eval/golden/requirements_V*.json`, T10).
- [ ] Все `source_fragment_ids` валидны, предупреждений о непокрытых фрагментах нет.
- [ ] 5 вакансий с hh.ru из других профессий: прогон без ошибок, требования выглядят разумно, описание в `eval/notes.md`.
- [ ] Вакансия сплошным текстом без заголовков разбирается.
- [ ] `make check-leak` чистый.
- [ ] Тесты: атомаризация, альтернативы, маркеры побеждают модель, обязанности → nice, дубли, покрытие.
