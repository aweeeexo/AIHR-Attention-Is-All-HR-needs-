## Главное

В топ-3 проходят только по техническим критериям (100 баллов), поэтому сначала закрываем их все, а киллер-фичи делаем после. Отраслевые 30 баллов ставят уже на защите и только тройке лидеров. Полный текст кейса меняет наш прежний план в пяти местах.

1. **Направление обратное.** На входе одно резюме и набор вакансий, на выходе рейтинг вакансий для кандидата. Мы раньше думали про «одна вакансия, много резюме». Балл должен быть сравним между вакансиями с разным числом требований.
2. **20 баллов из 100 дают за Docker, README и описание архитектуры.** Это самые дешёвые баллы в кейсе. Docker поднимаем в первый час, а не в последний.
3. **Почти половина баллов завязана на доказательства и статус «не указано».** Критерии 2, 4 и первый пункт критерия 5 дают 41 балл за одно и то же умение: связать требование с фрагментом резюме и не выдумать вывод там, где фрагмента нет.
4. **Жюри, скорее всего, запустит решение на своих документах.** В критериях прямо сказано про новые резюме и вакансии другой структуры, пустые и повреждённые файлы и про запуск в чистом окружении. Подгонка под три вакансии из набора стоит баллов (критерий 3, «без ручной настройки под отдельный документ»).
5. **Вакансии из трёх несвязанных областей:** frontend, учёт основных средств, куратор образовательного процесса. Никаких словарей под IT. Вся логика общая.

ФИО в резюме выдуманы, но ограничение про внешние API остаётся. Маскирование персональных данных перед вызовом LLM всё равно делаем: оно дешёвое и показывает, что решение готово к реальным резюме.

**Что спросить у организаторов сегодня:**

- [ ] С каким LLM-ключом жюри будет запускать решение: своим, нашим или нужен режим совсем без внешних API?
- [ ] Считаются ли резюме из набора открытыми данными, которые можно отправлять во внешний API?
- [ ] В каком формате резюме (docx, pdf) и будут ли при проверке другие форматы?
- [ ] Нужен ли веб-интерфейс или достаточно API и файла с отчётом?
- [ ] Есть ли ограничения на железо при проверке (GPU, память, доступ в интернет)?

## Сквозная архитектура

LLM делает только две вещи: извлекает структуру из текста и выносит вердикт по одному требованию. Всё, что можно посчитать или проверить без модели, делает код: цитаты, стаж, пороги, балл, рейтинг. Такое разделение прямо отвечает требованию кейса «оценка объяснима и опирается только на информацию из резюме и вакансий».

[схема не перенесена: поток данных · 4 этапа, 12 шагов]

Данные идут слева направо внутри этапа и сверху вниз между этапами. Во внешний API уходит только текст после маскирования, этапы 2 и 3.

Три принципа, на которых держится схема:

- **Каждый фрагмент имеет адрес.** При парсинге режем документ на пронумерованные фрагменты (R1, R2… для резюме, V1, V2… для вакансии). Модель ссылается на номера, а текст цитаты подставляет код.
- **Статус и балл нельзя получить без доказательства.** Нет валидного фрагмента — код ставит «не указано», что бы ни написала модель.
- **Все промежуточные результаты — JSON по схеме.** Их можно показать, протестировать и закэшировать по хэшу документа. Повторный запуск на тех же файлах даёт тот же ответ.

## Критерий 1. Извлечение требований и фактов (16 баллов)

Баллы дают за два отдельных результата: список требований каждой вакансии с делением на обязательные и желательные (8) и факты из резюме (8). Оба должны быть видны жюри как самостоятельные блоки в интерфейсе и в JSON, иначе оценить их нечем.

### Лучшие практики

- **Строгая схема вместо «верни JSON».** Извлечение по промпту без схемы ломается в 5–20% случаев в зависимости от сложности схемы ([Tian Pan](https://tianpan.co/blog/2025-10-29-structured-outputs-llm-production)). Стандарт сейчас: встроенный structured output провайдера (constrained decoding) + валидация Pydantic + повтор запроса с текстом ошибки ([Tian Pan](https://tianpan.co/blog/2025-11-10-structured-output-production-llms)).
- **Схема гарантирует форму, но не смысл.** Constrained decoding даёт валидный JSON, но значения могут быть неверными ([MLflow](https://mlflow.org/articles/structured-outputs-llm/)). Поэтому каждое извлечённое требование и факт несёт номер исходного фрагмента, и код проверяет, что такой фрагмент есть.
- **Сначала рассуждение, потом поля.** Для классификаций внутри схемы работает паттерн «поле reasoning первым» ([Tian Pan](https://tianpan.co/blog/2025-11-10-structured-output-production-llms)). У нас это короткое обоснование перед полем must / nice.
- **Парсер под задачу, а не самый умный.** В независимом бенчмарке Docling занимает 1032 МБ, MarkItDown 251 МБ ([dev.to](https://dev.to/nhirschfeld/i-benchmarked-4-python-text-extraction-libraries-2025-4e7j)). Для простых DOCX лёгкий MarkItDown проще в установке и примерно так же точен ([file2markdown](https://www.file2markdown.ai/blog/markitdown-alternatives)). Наши вакансии — обычные docx, тяжёлый парсер только раздует Docker-образ.
- **Разделение must-have и nice-to-have — стандарт структурированного найма.** Greenhouse советует держать в оценочной карте «need to have», а «nice to have» явно помечать ([Greenhouse](https://ww2.greenhouse.io/guidance/how-to-implement-structured-hiring-steps-2-and-3-defining-your-scorecard-and-planning-your-interview)).

### Воспроизводимость извлечения

- Температура 0 и фиксированная версия модели в переменных окружения.
- Кэш по хэшу «текст документа + версия промпта»: вакансия разбирается один раз, а не на каждое резюме.
- Few-shot примеры берём из других областей (логистика, продажи), а не из трёх вакансий кейса. Иначе это подгонка.
- Проверка качества: вручную выписать требования трёх вакансий и факты четырёх резюме, сравнить с выводом системы, посчитать полноту и точность. Эта разметка займёт пару часов и пригодится во всех остальных критериях.

### Лучшие практики

- **Модель выбирает фрагмент, текст подставляет код.** Это deterministic quoting: LLM указывает, какой кусок источника цитировать, а сам текст достаётся обычным поиском и никогда не проходит через модель ([Simon Willison](https://blog.simonwillison.net/2024/May/7/deterministic-quoting/), [Matt Yeung](https://mattyyeung.github.io/deterministic-quoting)). Выдумать цитату при такой схеме невозможно.
- **Проверка после генерации — это шлюз, а не украшение.** Если ни одна ссылка не прошла проверку, ответ понижается до «не найдено» ([Vaquill](https://www.vaquill.ai/engineering/verify-ai-citations-in-code)). У нас это превращается в статус «не указано».
- **Ссылка не гарантирует верного прочтения.** Ответ с цитатой всё ещё может неверно истолковать источник ([CallSphere](https://callsphere.ai/blog/how-citation-grounding-works-inside-a-claude-agent)). Отсюда второй слой: отдельная проверка «фрагмент действительно подтверждает требование».
- **Проверку подтверждения можно делать маленькой моделью.** MiniCheck (770 млн параметров) выходит на точность GPT-4 в проверке утверждений по документу ([arXiv](https://arxiv.org/html/2404.10774v1)). Она англоязычная ([PromptLayer](https://www.promptlayer.com/models/minicheck-roberta-large)), поэтому для русского берём идею, а не модель: второй вызов LLM с узким вопросом или многоязычная NLI-модель.
- **Оценка по одному требованию, а не «сравни два документа».** Так работает evaluation-агент LinkedIn: квалификации отдельно, по каждой вердикт с доказательством (см. наш первый документ).

| Второй проход проверяющего: «доказывает ли фрагмент R7 требование V3: да / частично / нет». Несогласие с первым проходом → пометка «проверить вручную» | Ловит неверное прочтение фрагмента | M |
| Три прогона и голосование для спорных требований | Устойчивость статусов. Но дороже и медленнее | M |
| Явные отрицания в резюме: «без опыта руководства», «английский: базовый» | Редкий случай, когда «не соответствует» доказано прямо | S |

### Как проверить себя

У нас 4 резюме и 3 вакансии, то есть 12 пар. Размечаем вручную статус каждого требования в каждой паре и считаем матрицу ошибок 4×4. Главная ячейка — сколько раз система поставила «не соответствует» там, где правильно «не указано». Эту разметку кладём в репозиторий как регрессионный тест: золотой набор, детерминированные проверки и порог качества — стандартный способ не сломать промпт правкой ([TestDino](https://testdino.com/blog/llm-evaluation-framework)).

## Критерий 3. Ранжирование вакансий (16 баллов)

Рейтинг считает код по одной формуле из статусов критерия 2, а LLM в ранжировании не участвует. Так закрываются все три подпункта: порядок по рассчитанным показателям (8), объяснимая причина места (5), единая логика без ручной настройки (3).

### Базовая формула

```latex
S = 100 \cdot \frac{\sum_i w_i \, v_i}{\sum_i w_i}, \qquad v_i = \begin{cases} 1 & \text{соответствует} \\ p_i & \text{частично} \\ 0 & \text{не соответствует} \\ u & \text{не указано} \end{cases}
```

- Вес w: обязательное требование 3, обязанность 2, желательное 1. Значения лежат в одном конфиге и одинаковы для всех вакансий.
- Частичное p: 0,5 по умолчанию. Для требований с числовым порогом — доля от порога: 1,5 года при требуемых 3 дают 0,5.
- «Не указано» u: 0,5 в основном балле, то есть нейтрально. Дополнительно считаем границы: u = 0 даёт минимум, u = 1 даёт максимум.

Рекрутер видит строку вида «Соответствие 68%, от 52% до 84% в зависимости от 4 неуказанных требований». Интервал честно показывает неопределённость и сразу объясняет, зачем нужны вопросы кандидату.

### Лучшие практики

- **Взвешенная оценочная карта.** В структурированном найме обязательный навык весит больше желательного, чтобы кандидат не набрал высокий балл на второстепенном ([Truffle](https://hiretruffle.com/blog/create-interview-scorecard), [JobScore](https://jobscore.com/articles/interview-scorecards)).
- **Нокаут-критерии.** В ряде шаблонов провал по обязательной компетенции автоматически даёт «не продолжать» ([MyJobMag](https://www.myjobmag.com/resources/interview-scorecard-tool-2)). Без такого разделения кандидат может набрать много на желательном и пропустить жёсткое требование ([Apps365](https://www.apps365.com/?p=143345)).
- **Рейтинг не доверяем LLM.** У LLM-судей задокументировано смещение по позиции и длине текста (см. раздел про AI safety в первом документе). Просьба «упорядочи три вакансии» даёт необъяснимый и невоспроизводимый порядок.

### Пул идей: как считать

| Идея | Что даёт | Минусы |
| --- | --- | --- |
| «Не указано» = 0,5 плюс интервал (рекомендую) | Нейтрально, честно, объяснимо одной фразой | Нужно показывать три числа вместо одного |
| «Не указано» исключаем из формулы, отдельно показываем полноту данных | Балл считается только по фактам | Пустое резюме с одним совпадением получает 100% |
| Ранжирование по нижней границе | Осторожно, нет завышенных ожиданий | По сути трактует молчание как отсутствие. Риск потерять 5 баллов критерия 5 |
| Два ключа сортировки: сначала доля закрытых обязательных, потом общий балл | Понятно рекрутеру: «сначала обязательное» | Желательные почти не влияют |
| Флаг блокирующего пробела: обязательное со статусом «не соответствует». На место не влияет, но меняет метку рекомендации | Рекрутер сразу видит стоп-фактор | Нужна аккуратность с разметкой must |
| Подбаллы по категориям: опыт, навыки, образование | Совпадает с формулировкой кейса «по опыту, образованию и навыкам» | Больше чисел на экране |
| Метка рекомендации по порогам из конфига: «подходит», «подходит с оговорками», «не подходит» | Лучшая из плохих вакансий не выдаётся за хорошую | Пороги надо обосновать |
| Проверка устойчивости: меняем веса на ±1 и смотрим, меняется ли порядок | Готовый ответ на вопрос жюри «почему веса именно такие» | Полчаса работы |

### Пул идей: как объяснять место

- **Разбор балла по строкам.** Рядом с вакансией: «закрыто 5 из 6 обязательных, 2 из 4 желательных, 1 не указано». Каждое число кликабельно и ведёт в таблицу требований.
- **Три главных плюса и три главных минуса.** Требования с наибольшим вкладом в балл и с наибольшей потерей. Выбирает код по величине w·v.
- **Сравнение с соседом по рейтингу.** «Выше вакансии 2 на 31 пункт: там не подтверждены 3 обязательных требования по учёту». Строится шаблоном из чисел.
- **Объяснение строит шаблон, а не LLM.** Тогда в нём не может появиться выдуманный факт. LLM можно дать переписать текст глаже, но с проверкой из критерия 4.
- **Формула видна пользователю.** Кнопка «Как посчитано» с формулой и весами из конфига. Это прямое доказательство «единой логики без ручной настройки».

Чтобы не потерять 3 балла за единую логику: в коде и промптах нет ни одного упоминания frontend, основных средств или куратора. Проверяем поиском по репозиторию перед сдачей.

## Критерий 4. Проверяемый результат для рекрутера (12 баллов)

Отчёт собирается из уже проверенных вердиктов, а не пишется моделью с нуля. Баллы дают за ссылки на фрагменты обоих документов (5), наличие сильных сторон, пробелов, рисков и вопросов (4), отсутствие выдуманных фактов в рекомендациях и тексте для коммуникации (3).

### Лучшие практики

- **Цитата не проходит через модель.** Единственный способ гарантировать, что LLM не изменила текст, — не пропускать его через LLM ([Simon Willison](https://blog.simonwillison.net/2024/May/7/deterministic-quoting/)). В интерфейсе цитаты визуально отделены от сгенерированного комментария ([Matt Yeung](https://mattyyeung.github.io/deterministic-quoting)).
- **Нормализация при сверке цитат — только типографская.** Unicode NFKC, кавычки, тире, неразрывные пробелы, регистр. Стемминг и синонимы в проверке цитат ведут к подтверждению несуществующей цитаты ([Vaquill](https://www.vaquill.ai/engineering/verify-ai-citations-in-code)).
- **Сначала доказательства, потом текст.** Подход FRONT: сперва модель выбирает подтверждающие цитаты, затем пишет ответ, согласованный с ними ([OwnYourAI](https://ownyourai.com/?p=32069)). У нас роль цитат играет таблица вердиктов.
- **Непроверенное утверждение не доходит до пользователя.** Выводы, которые нельзя привязать к источнику, помечаются или удаляются ([Zen van Riel](https://zenvanriel-blog.pages.dev/glossary/grounding)).

### Пул идей: связь с фрагментами (5 баллов)

| Идея | Что даёт | Сложн. |
| --- | --- | --- |
| В каждой строке таблицы две цитаты: из вакансии (откуда требование) и из резюме (чем подтверждено), с адресом «раздел, абзац» | Критерий требует фрагменты и резюме, и вакансии | S |
| Просмотр документа с подсветкой: клик по строке таблицы прокручивает резюме к фрагменту | Сильный момент демо, проверка за секунду | M |
| Счётчик в отчёте: «все N цитат найдены в исходных документах» | Одна строка, которая показывает проверяемость | S |
| Для расчётов показываем формулу: «03.2021–06.2024 = 3 года 3 месяца, требуется 3 года» | Вывод проверяем без доверия к модели | S |
| Экспорт отчёта в DOCX или PDF с теми же цитатами | Рекрутер пересылает руководителю | S–M |

### Пул идей: сильные стороны, пробелы, риски, вопросы (4 балла)

| Блок | Из чего собираем | Идеи |
| --- | --- | --- |
| Сильные стороны | Обязательные требования со статусом «соответствует» | Перевыполнение порога («5 лет при требуемых 2»). Факты сверх требований, релевантные вакансии. Достижения с цифрами из резюме |
| Пробелы | Обязательные со статусом «не соответствует» и «частично» | Для «частично» — чего именно не хватает. Пометка «закрывается обучением» для смежных навыков |
| Риски | Обязательные со статусом «не указано» плюс факты, посчитанные кодом | Перерывы в стаже больше N месяцев. Навык только в списке, без подтверждения опытом. Навык не использовался давно. Смена профиля. Формулировка всегда «стоит уточнить», без оценок личности |
| Вопросы кандидату | Каждое «не указано» и «частично» по обязательным | Привязка вопроса к требованию. Два типа: фактический («работали ли вы с 1С: Учёт ОС?») и поведенческий («расскажите о последней инвентаризации, которую вы проводили»). Приоритет по весу требования, 3–7 вопросов |
| Рекомендация рекрутеру | Метка из ранжирования + блоки выше | Следующий шаг: пригласить, уточнить по телефону, предложить другую вакансию из рейтинга. Что проверить на интервью в первую очередь |

### Пул идей: тексты без выдуманных фактов (3 балла)

| Идея | Как работает | Сложн. |
| --- | --- | --- |
| Шаблоны со слотами (надёжный минимум) | Письмо кандидату и рекомендация собираются из шаблона, в слоты подставляются названия требований и факты из таблицы. Выдумать нечего | S |
| LLM пишет только по структуре | На вход модели идёт не резюме, а JSON проверенных вердиктов. Инструкция: использовать только переданные факты | S |
| Проверка сущностей кодом | Все числа, даты, названия технологий, компаний и вузов из сгенерированного текста должны найтись в исходных фактах. Не нашлись → перегенерация, потом откат к шаблону | M |
| Проверка утверждений моделью | Каждое предложение письма проверяется на подтверждение фактами (идея MiniCheck). Неподтверждённое удаляется | M |
| Пометка происхождения в интерфейсе | Цитаты из документов и сгенерированный текст выглядят по-разному | S |
| Тест на выдумки | В золотом наборе: резюме без образования и без дат. В письме и рекомендации не должно появиться ни вуза, ни стажа | S |

Минимум на все 12 баллов: две цитаты в каждой строке, четыре блока отчёта из статусов, шаблонное письмо с проверкой сущностей.

## Критерий 5. Неопределённость и надёжность (12 баллов)

Три независимые задачи: не превращать молчание резюме в «нет навыка» (5), работать на незнакомых документах (4), не падать на плохих файлах (3). Первую решает архитектура, вторую — тесты на чужих данных, третью — лестница проверок на входе.

### «Не указано» ≠ «нет» (5 баллов)

**Почему нельзя положиться на модель.** Бенчмарк AbstentionBench (NeurIPS 2025) проверил 20 фронтирных LLM: умение воздержаться от ответа остаётся нерешённой проблемой, размер модели почти не помогает, а дообучение на рассуждения часто его ухудшает ([Hugging Face](https://huggingface.co/papers/2506.09038)). Модель склонна «додумать» ответ. Поэтому статус «не указано» у нас обеспечивает код.

| Идея | Как работает | Сложн. |
| --- | --- | --- |
| Правило «нет фрагмента → не указано» в коде | Любой вердикт без валидного номера фрагмента принудительно переписывается | S |
| «Не соответствует» требует контр-фрагмента | В схеме ответа для этого статуса обязательно поле с фрагментом, который показывает несоответствие | S |
| Явный вариант «не указано» в перечислении статусов и примеры в промпте | «Не указано» — полноправный правильный ответ, а не отказ. Так устроен набор Abstain-QA: у каждого вопроса есть явный вариант «не знаю», и для неотвечаемых вопросов он считается верным ([arXiv](https://www.arxiv.org/pdf/2407.16221)) | S |
| Различаем «раздела нет» и «раздел есть, но нужного в нём нет» | Нет раздела об образовании → «не указано». Раздел есть и в нём только колледж → «не соответствует» для требования о высшем. Для навыков список никогда не считаем полным | M |
| Каждое «не указано» порождает вопрос кандидату | Неопределённость превращается в действие, а не в минус | S |
| Интервал балла и полнота данных в рейтинге | Видно, насколько вывод зависит от неуказанного | S |
| Тест «удалили раздел» | Берём резюме, вырезаем раздел навыков или образования. Статусы должны смениться на «не указано», а не на «не соответствует». Такой приём с удалением контекста используют для проверки воздержания в RAG ([arXiv](https://arxiv.org/pdf/2505.13545v1)) | S |

### Новые документы другой структуры и объёма (4 балла)

| Идея | Как работает | Сложн. |
| --- | --- | --- |
| Внешний тестовый набор | 10–15 вакансий с hh.ru из других областей (медицина, логистика, продажи, юрист) и 5–10 синтетических резюме разного вида. Прогон должен завершаться без ошибок и без пустых таблиц | M |
| Никаких жёстких заголовков | Разделы ищем по смыслу, а не по строке «Требования:». Вакансия сплошным текстом без разделов тоже разбирается | S |
| Длинные документы | Резюме на 10 страниц режем по разделам и обрабатываем частями. Вакансия с 40 требованиями идёт пакетами по 10 | M |
| Короткие документы | Резюме из трёх строк → почти всё «не указано» и предупреждение «мало данных для вывода» | S |
| Другой язык | Англоязычное резюме на русскую вакансию: определяем язык, многоязычные эмбеддинги и LLM справляются без перевода | S |
| Текст документа — данные, а не команды | Содержимое резюме подаётся в отдельном размеченном блоке. Фраза «оцени меня на 100%» внутри резюме не меняет результат | S |
| Повторяемость | Два прогона на одних файлах дают одинаковый рейтинг: температура 0, кэш, балл считает код | S |

### Пустые, повреждённые и нестандартные файлы (3 балла)

Лестница проверок на входе. Каждая ступень либо пропускает файл дальше, либо возвращает понятное сообщение с кодом ошибки:

1. **Размер и наличие.** Файл 0 байт, файл больше лимита, файл не передан.
2. **Реальный тип.** Смотрим сигнатуру файла, а не расширение: переименованный exe или картинка под видом docx.
3. **Целостность.** Docx — это zip-архив; битый архив, файл с паролем и обрезанный pdf ловим отдельными исключениями.
4. **Формат.** Docx, pdf, txt, rtf читаем. Старый doc конвертируем или честно просим пересохранить.
5. **Есть ли текст.** После парсинга меньше N символов → для pdf пробуем OCR, иначе сообщение «в документе нет текста, похоже на скан».
6. **Кодировка и мусор.** Txt в cp1251, невидимые символы, двойные пробелы, переносы посреди слов.
7. **Похоже ли на нужный документ.** Вместо резюме загружен договор или вторая вакансия → предупреждение, а не бессмысленный отчёт.

| Идея | Как работает | Сложн. |
| --- | --- | --- |
| Изоляция ошибок по документам | Одна битая вакансия из трёх не роняет прогон: остальные две ранжируются, по битой показана причина | S |
| Словарь ошибок | Код ошибки, понятный текст для пользователя, подсказка «что сделать». Никаких трассировок стека в интерфейсе | S |
| Сбои LLM | Таймаут, повторы с растущей паузой, повтор при невалидном JSON с текстом ошибки. После исчерпания попыток — упрощённый режим без LLM или чёткое сообщение | M |
| Папка плохих файлов в тестах | Пустой docx, 0 байт, битый zip, pdf-скан, pdf с паролем, txt в cp1251, картинка с расширением docx, резюме-таблица, файл на 200 страниц. На каждый файл тест pytest | S |
| Страница «что пошло не так» в демо | На защите загружаем битый файл и показываем аккуратное сообщение. Дешёвый способ показать 3 балла живьём | S |

## Критерий 6. Развёртываемость и воспроизводимость (20 баллов)

Это пятая часть всех технических баллов, и для неё не нужен ML. Жюри берёт чистую машину, идёт по README и не правит код. Если на любом шаге что-то падает, теряются не только эти 20 баллов: остальные критерии проверить будет не на чем.

### Лучшие практики Docker

- **Многоступенчатая сборка.** Сборочные зависимости остаются в первом этапе, в итоговый образ попадает только то, что нужно для запуска ([Tessl](https://tessl.io/registry/skills/github/rohitg00/awesome-claude-code-toolkit/docker-best-practices)).
- **Не root, закреплённые версии, .dockerignore.** Отдельный пользователь через USER, базовый образ с конкретным тегом, исключение .git и .env из контекста сборки ([Tessl](https://tessl.io/registry/skills/github/rohitg00/awesome-claude-code-toolkit/docker-best-practices)).
- **HEALTHCHECK и depends\_on по здоровью.** Компоненты стартуют в правильном порядке и видно, что сервис жив ([skills.sh](https://skills.sh/rohitg00/awesome-claude-code-toolkit/docker-best-practices)).
- **Секреты только через окружение.** Ключ API не запекается в образ; передаётся через .env, который в .gitignore ([блог Harshit Gupta](https://harshitgupta5290.github.io/portfolio/blog/docker-python-microservices-production)).

## Ограничение кейса: внешние API и конфиденциальные данные

Во внешние API можно передавать только открытые данные. Вакансии открыты по своей природе. В резюме конфиденциальны персональные данные: ФИО, контакты, адрес, дата рождения, фото. В наборе кейса ФИО выдуманы, но решение должно работать и на настоящих резюме, поэтому строим защиту как для настоящих.

| Вариант | Как работает | Плюсы | Минусы |
| --- | --- | --- | --- |
| A. Маскирование + внешний API (основной) | Локально заменяем ПДн на токены, наружу уходит обезличенный текст, ФИО возвращаются в отчёт локально | Лучшее качество модели, лёгкий образ | Нужен ключ и интернет. Маскирование может пропустить редкий идентификатор |
| B. Полностью локально (профиль `local`) | Открытая модель в соседнем контейнере, ни одного внешнего вызова | Ограничение закрыто по построению. Работает без ключа | Медленнее без GPU, качество ниже, образ тяжелее |
| C. Гибрид | Вакансии разбирает внешний API (данные открытые), резюме обрабатывает локальная модель | Резюме не покидает контур даже в обезличенном виде | Две модели, сложнее отлаживать |

Рекомендация: делаем A как основной режим и B как переключатель в .env. Код один, меняется только адрес модели.

### Пул идей

| Идея | Что даёт | Сложн. |
| --- | --- | --- |
| Маскирование в два слоя: регулярки (телефон, email, ссылки, дата рождения) + NER для ФИО и адресов (Natasha) | Базовое закрытие ограничения | S |
| ФИО берём ещё и из имени файла и первой строки резюме, затем вычищаем все вхождения по тексту | NER может пропустить редкую фамилию, этот приём нет | S |
| Фото и метаданные docx (автор, компания) отбрасываем на этапе парсинга | Наружу не уходит то, что не нужно для оценки | S |
| Журнал исходящих запросов: файл или вкладка «что ушло во внешний API» с точным текстом | Соблюдение ограничения можно проверить, а не принять на веру. Хорошая фича для защиты | S |
| Контрольный фильтр перед отправкой: если в исходящем тексте остался email, телефон или найденное ФИО, запрос блокируется | Вторая линия защиты от ошибки маскирования | S |
| Слепой режим: по переключателю скрываем ещё и названия компаний и вузов | Меньше данных наружу и нет смещения к престижным брендам | S |
| Тест маскирования: четыре резюме кейса, в исходящих запросах нет ни одного ФИО и контакта | Доказательство для README и защиты | S |

В README в разделе «Внешние сервисы» пишем прямо: какой сервис вызывается, какие поля туда попадают, что маскируется, как включить полностью локальный режим. Подробности про инструменты маскирования есть в первом документе, раздел «Архитектура с защитой ПДн».

### Дополнительные возможности с показанной ценностью (5 баллов)

Критерий требует не просто фичу, а «показанную ценность». У каждой идеи ниже указано, чем её доказать.

| Фича | Чем показать ценность | Сложн. |
| --- | --- | --- |
| Пакетный режим: все резюме × все вакансии, матрица баллов 4×3 | Рекрутер видит лучшую вакансию для каждого кандидата и лучшего кандидата для каждой вакансии за один запуск | S |
| Журнал «что ушло во внешний API» | Показать запрос без ФИО и контактов: ограничение кейса соблюдено проверяемо | S |
| Письмо кандидату с уточняющими вопросами, готовое к отправке | Экономит рекрутеру шаг; показать, что в письме нет ни одного факта вне резюме | S |
| «Что если»: кандидат ответил на вопрос, рекрутер отмечает ответ, балл и рейтинг пересчитываются | Показать, как один ответ меняет интервал 52–84% на точное число | M |
| Проверка качества вакансии: расплывчатые и непроверяемые по резюме требования | Пример на вакансии кейса: «это требование по резюме проверить нельзя, выносим в интервью» | S |
| Защита от скрытого текста в резюме | Загрузить резюме с белым текстом и показать предупреждение | S–M |

| Собственная метрика качества: точность статусов на ручной разметке 12 пар | Один слайд с матрицей ошибок. Мало кто из команд принесёт цифры | S |

Мой выбор на три места: пакетный режим, журнал внешних запросов, «что если» с пересчётом. Они дешёвые, наглядные и продолжают основную логику, а не висят сбоку.

### План развития и внедрения (5 баллов)

Критерий просит «реалистичный план с учётом ограничений решения». Сначала честно называем ограничения, потом показываем, как каждое снимается.

| Ограничение сейчас | Шаг развития | Горизонт |
| --- | --- | --- |
| Качество проверено на 12 парах | Пилот в одном подразделении МФТИ: 50–100 реальных пар, рекрутер правит статусы, считаем совпадение с человеком | 1 месяц |
| Файлы загружаются вручную | Интеграция с кадровой системой и почтой: отклики попадают в систему сами, отчёт прикрепляется к карточке кандидата | 2–3 месяца |
| Внешний LLM API | Перевод на модель в контуре института; по правкам рекрутеров дообучаем небольшую локальную модель | 3–6 месяцев |
| Веса заданы экспертно | Калибровка весов и порогов по решениям рекрутеров в пилоте | 2–3 месяца |
| Нет проверки на предвзятость на реальных данных | Регулярный тест: меняем имя, пол, возраст в резюме, балл не должен меняться | 1–2 месяца |
| Только резюме и текст вакансии | Обратное направление (лучшие кандидаты для вакансии из базы прошлых откликов), профили научных сотрудников с публикациями | 6+ месяцев |
| Решение принимает человек | Это не ограничение, а принцип: система готовит доказательства, отказывает и приглашает рекрутер | всегда |

### Выступление (4 балла)

1. **Боль, 30 секунд.** Рекрутер сверяет резюме с требованиями вручную и не доверяет «проценту совпадения» без объяснений.
2. **Демо, 2 минуты.** Загрузка резюме → рейтинг трёх вакансий → клик по требованию с подсветкой цитаты → вопросы кандидату.
3. **Почему этому можно верить, 1 минута.** Цитаты подставляет код, «не указано» ставит код, балл считает код. Матрица ошибок на ручной разметке.
4. **Архитектура и ограничение по данным, 1 минута.** Схема из четырёх этапов, журнал внешних запросов, локальный режим.
5. **Дополнительные возможности, 1 минута.** Две-три фичи, каждая с примером пользы.
6. **Ограничения и план, 1 минута.** Таблица выше в сжатом виде.

Один докладчик, один человек на демо. Прогоняем дважды на время. Готовим ответы на три ожидаемых вопроса: «чем вы лучше простого запроса в ChatGPT», «что будет на резюме другой профессии», «куда уходят персональные данные».

## Схемы данных

Полные контракты v1 (Pydantic) лежат в репозитории в `docs/contracts.md`. Цепочка основных структур:

| Структура | Что хранит | Кто заполняет |
| --- | --- | --- |
| `Fragment` | Фрагмент документа с адресом (`R12`, `V2.7`), ролью раздела, исходным и обезличенным текстом | код |
| `Requirement` | Атомарное требование: тип, must / nice с обоснованием, порог, альтернативы, фрагменты вакансии | LLM + код |
| `CandidateProfile` | Места работы с датами и уровнем задач, образование, навыки с типом упоминания, языки | LLM + код (даты, стаж, уровни) |
| `Verdict` | Статус, тип доказательства, фрагменты и цитаты, цепочка вывода, расчёт правила, уверенность | LLM + шлюз кода |
| `VacancyScore`, `Ranking` | Балл, интервал, счётчики, блокирующие пробелы, метка, объяснение | код |
| `Report` | Таблица требований с цитатами из обоих документов, сильные стороны, пробелы, риски, вопросы, рекомендация, письмо, статистика проверки | код + LLM с проверкой сущностей |
| `MatchResult` | Всё вместе плюс ошибки по файлам и путь к журналу исходящих запросов | код |
